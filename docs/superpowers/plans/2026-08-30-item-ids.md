# Item ids Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every note this plugin creates carries a `pbl-id` frontmatter property — one integer, unique in the vault, written in the same atomic `vault.create` that makes the note.

**Architecture:** One new pure module, `src/domain/itemIds.ts`, holds the key and answers "what is the next id" by scanning the vault's markdown frontmatter for the highest existing value. The four note creators in `src/storage/` each gain one line into the frontmatter object they already build. Nothing reads the id back, nothing renders it, and no existing note is written to.

**Tech Stack:** TypeScript, Obsidian plugin API (`App`, `TFile`, `metadataCache`, `vault`), vitest with the repository's `FakeVault` double.

## Global Constraints

Copied from `CLAUDE.md` and the spec — every task's requirements include these.

- `npm run check` must pass: build + lint + coverage-thresholded tests + fallow + docs register. All five, before every commit.
- Layering is `main → commands → view → storage → domain`, enforced by `eslint.config.mjs`. `storage/` may import `domain/`; `domain/` may import neither.
- 400-line cap per `src/` file, 450 per `test/` file, enforced by lint.
- Nothing outside `src/storage/` may call `vault.create` — enforced by `no-restricted-syntax`.
- Every module in `src/` must be *specified* by a use case's `## Where it lives` or an ADR's `## Decision`, checked by `scripts/docs-check.mjs` rule 7.
- Coverage thresholds in `vitest.config.mts` only ever go up.
- No new user-facing sentence, so the `i18n/` catalog gains no keys.
- `CHANGELOG.md` gains an `[Unreleased]` entry in the same pull request.
- The key is the literal string `pbl-id`. It is **not** a row in `src/domain/optionalProperties.ts` and gets no view option, no `configProblems` row, no backfill stub and no picker entry.

- [ ] **Step 4: Write the module**

Create `src/domain/itemIds.ts`:

```ts
import { App } from 'obsidian';

/**
 * The id a note this plugin creates carries, and the one question about it: what the
 * next one is.
 *
 * A FIXED key, and the only write target in `src/` that is not a row in
 * `optionalProperties.ts`. Those rows exist to name a property a vault ALREADY has and
 * to gate a feature that cannot run until somebody points at it. An id names nothing
 * that pre-exists: the plugin invents the value, writes it once at creation, and never
 * reads it back to decide anything. A configurable key would add a fifth reader to that
 * table and one more way for this to be switched off, in exchange for renaming a
 * property nothing else in the vault refers to. The `pbl-` prefix is this plugin's own
 * namespace, and that one word is the whole collision surface.
 */

/** The frontmatter key every note this plugin creates carries. */
export const ITEM_ID_KEY = 'pbl-id';

/**
 * The highest id this session has already handed out, per vault.
 *
 * A floor on a READ, never a source of truth. `metadataCache` catches up
 * asynchronously, so two creations in one tick both scan a vault that knows about
 * neither and would take the same maximum; the floor is what stops the second one
 * repeating the first. It only ever moves up, a reload re-derives it from the vault,
 * and a vault whose ids were edited by hand or restored from a backup overrules it —
 * `Math.max` below reads the scan first.
 *
 * Keyed by `App` rather than held as one number so a second vault cannot inherit the
 * first's count. That is also what keeps the suite honest: each test's fake gets its own
 * floor without a reset hook, so nothing here needs an export that only a test calls.
 */
const floors = new WeakMap<App, number>();

/**
 * The next id for this vault: one past the highest that either the vault holds or this
 * session has issued.
 *
 * Deriving it from the Base's RESULTS was refused twice over — the context-row rule
 * forbids it, and a note the filter excluded still holds an id, so skipping it would
 * hand the next creation a number already on disk. A persisted counter was refused for a
 * different reason: two devices on a synced vault would each hold their own and both
 * would issue the same number. The vault is the only copy of this state both devices see.
 *
 * A value that is not a whole finite number is ignored rather than allowed to poison the
 * maximum: `pbl-id: ""` is what a hand-edited note or a stubbed key looks like, and
 * `NaN` propagated through `Math.max` would make every later id `NaN`.
 *
 * ponytail: one `getFileCache` per markdown file per creation, against a cache Obsidian
 * already holds in memory. A creation is a user gesture, so this is cheap at backlog
 * scale; a vault large enough to feel it would want the scan narrowed to the folders the
 * plugin writes into.
 */
export function nextItemId(app: App): number {
	let highest = floors.get(app) ?? 0;
	for (const file of app.vault.getMarkdownFiles()) {
		const value = Math.floor(Number(app.metadataCache.getFileCache(file)?.frontmatter?.[ITEM_ID_KEY]));
		if (Number.isFinite(value) && value > highest) highest = value;
	}
	const next = highest + 1;
	floors.set(app, next);
	return next;
}
```

# Every created note carries an id

**As** someone who talks about the backlog outside Obsidian, **I want** every note this
plugin makes to carry a short number of its own, **so that** I can name one item in a
commit message, a chat or a standup without pasting a title that is going to change.

## Use case

| | |
| --- | --- |
| **Actor** | Anyone creating a note through the plugin |
| **Trigger** | Any creation the plugin performs: a work item, a resource, a release, an absence |
| **Preconditions** | None. This is not configurable and cannot be switched off |
| **Guarantee** | **No note that already exists is ever written to.** The id is assigned once, in the same single write that creates the note, and nothing changes it afterwards |

**Main flow**

1. Something asks the plugin to create a note.
2. The plugin reads the vault for the highest `pbl-id` any note already carries.
3. The new note's frontmatter is built with `pbl-id` one past that number, alongside
   everything else that creation writes.
4. The note is created in one write, carrying its id from the moment it exists.

**Extensions**

- **2a — no note in the vault carries an id.** The first one is `1`.
- **2b — a note carries a `pbl-id` that is not a whole number.** Ignored for the
  maximum. A blank key is what a hand-edited note looks like, and letting `NaN` through
  would make every later id `NaN` too.
- **2c — a note the Base filtered out carries a higher id.** Still counted. The number
  must be unique in the VAULT, so the scan reads the vault rather than the view's
  results — the one place the context-row rule's "never derived from the results" is
  satisfied by reading somewhere else entirely.
- **3a — two notes are created before Obsidian's metadata cache catches up.** The second
  does not repeat the first's number: the answer is one past the higher of what the vault
  holds and what this session has already issued.
- **4a — the creation is refused** (a release whose properties collide, an absence whose
  resource stopped being one). No note, and no id: the number is taken after the refusal,
  not before it.

## Acceptance criteria

- Every note the plugin creates carries `pbl-id`, and no note it does not create gains one.
- The value is an integer, unique in the vault, and one global sequence — a resource, a
  release and an Epic are numbered from the same run, with no type prefix.
- It is written in the same single `vault.create` as the type and the hierarchy, so a
  note without its id never exists on disk.
- Nothing reads the id back, renders it or matches on it, and no existing note is
  backfilled — not by the ✨ action either.
- The key is fixed and carries no view option, no collision report and no picker entry.

## What is deliberately not here

- **No backfill.** Existing notes gain nothing, not even from the ✨ action. Decided in
  the spec; adding it later is a change to `computeInitWrites`, not to this module.
- **Nothing renders the id.** Not in a row, not on a card, not in a tooltip. That is why
  this whole change adds no `i18n/` keys.
- **No search or lookup by id.** Obsidian's own search finds `pbl-id: 42` already.
- **The scan is not narrowed to the plugin's own folders.** Marked with a `ponytail:`
  comment naming the ceiling; a vault large enough to feel one cache read per markdown
  file per user gesture is where that becomes worth doing.
