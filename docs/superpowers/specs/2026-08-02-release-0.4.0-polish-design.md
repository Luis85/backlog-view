# Release 0.4.0 — improvement and polishing pass

The pass that runs before `0.4.0` is tagged. It is a **polish** pass in the strict sense:
it changes what the plugin *says about itself* and fixes one defect that has a rule
already written down three times. It adds no capability.

## Why it exists

`0.3.0` shipped a tree. `0.4.0` ships a tree, a kanban board and a roadmap — 357 commits,
two whole projections, the `Milestone` type, WIP limits, per-column policies and
transition date stamps. Every one of those is covered by tests, by the docs register and
by `npm run check`, which is green.

None of them is covered by the two documents a user actually reads: `README.md` and the
`description` in `manifest.json`. Both still describe `0.3.0`. That is the gap this pass
closes, plus the one open `Bug` in the register.

## Scope

In:

1. The axis-read defect — [[An axis property named off Object.prototype reads as unreadable]].
2. `README.md` — two new sections, three corrections.
3. `manifest.json` — the community-directory description.
4. The three `Smoke test the …` Feature notes — recording the maintainer's run.

Out, deliberately:

- **[[Split the view dispatch hub]].** Real and urgent for the *next* increment, invisible
  in this one. A refactor of the file every projection routes through does not belong in
  the commit range of a release being cut; it belongs first in the range after it.
- **Every documented limitation.** [[A dormant axis key still gates writes]],
  [[A renamed state orphans its limit]], [[Failed creation leaves its folder behind]],
  [[The backfill stubs a key a milestone may not touch]] and
  [[The today line swallows a row's clicks]] are each filed with the reasoning that
  chose them. Re-deciding any of them under release pressure is how a considered
  trade-off becomes an accident.
- **The smoke-test sub-issues.** See *Recording the smoke test* below.

## 1. The defect — state `ownValue` once

### What is wrong

`readGated` in `src/domain/model.ts` reads a configured axis key straight off the
frontmatter object:

```ts
return key ? read(fm?.[key]) : absentReading();
```

`__proto__`, `constructor`, `toString` and `valueOf` are legal frontmatter property
names. On a note that does not own the key, that lookup returns the inherited value from
`Object.prototype` — a function. `readString`, `readNumber` and `readTags` answer
"absent" to anything they do not recognise, so the state, type, order and tag reads
survive it by luck. The axis readers exist precisely to tell absent from unreadable, so
they answer **refused**: every note lacking the property lands on the shelf marked
unreadable, instead of simply unplanned.

### Why it is more than a one-line bug

The rule is already written down, correctly, three times:

| Where | Form |
| --- | --- |
| `readOwnKeys`, `src/domain/model.ts` | A comment, six lines below the function that breaks it |
| `ownValue`, `src/storage/frontmatter.ts` | A private function, correct |
| `readGated`, `src/domain/model.ts` | Neither — the defect |

`model.ts` states the rule in prose and then violates it in the function directly above
the prose. That is [[A comment that states a rule is not a check]] occurring inside the
same file as the comment, which makes "add a guard to `readGated`" the wrong fix: it
would leave the rule stated twice and enforced twice, with a third site free to get it
wrong again.

### The fix

Export **one** `ownValue` from `src/domain/noteFields.ts`, beside the readers that
consume it:

```ts
export function ownValue(fm: Record<string, unknown> | undefined, key: string): unknown {
	return fm !== undefined && Object.prototype.hasOwnProperty.call(fm, key) ? fm[key] : undefined;
}
```

Then:

- `readGated` in `src/domain/model.ts` calls it — this alone fixes **both** axis readers,
  because they share the call site.
- The `stateKey`, `typeKey`, `orderKey` and `tagsKey` reads in `src/domain/model.ts` call
  it too. They are correct today only because their readers happen to answer "absent" to
  a function; routing them through the helper removes the luck rather than relying on it.
- `readOwnKeys` in `src/domain/model.ts` calls it instead of spelling
  `Object.prototype.hasOwnProperty.call` inline.
- `src/storage/frontmatter.ts` **deletes** its private `ownValue` and imports this one.
  Storage may reach domain, and it already imports from this exact module.
- `resolveParent`, in `src/domain/noteFields.ts` itself, calls it **twice** — see below.

Net effect: one new export, one deleted duplicate, two defects closed, and the rule with
one home instead of five.

### The fifth site, found in review

`resolveParent` breaks the same rule in the same file the helper is being added to, and
in a **worse** way than `readGated` — found by Codex on PR #59, not by the audit that
wrote the rest of this section:

```ts
const raw: unknown = fm?.[parentKey];
// …
const keyPresent = !!fm && parentKey in fm;
return { file: null, hasValue: false, explicitRoot: keyPresent };
```

Two separate hazards, one line apart. `fm?.[parentKey]` is the familiar one. **`parentKey
in fm` is the sharper one: `in` walks the prototype chain by design**, so it is not merely
unsafe by accident the way an index read is — it answers `true` for `toString` on every
note in the vault, and no reader downstream can tell.

The consequence is larger than the axis bug's. With `parentProperty` named `toString`,
every note reads `explicitRoot: true` — the "pinned to top level" marker. That

- suppresses folder-note inference, so a folder-mode backlog loses its hierarchy
  (`outsideParentSeed` skips the inferred parent), and
- **admits every note in the vault to the hierarchy** under `hierarchyOnly`, since an
  explicit root is one of the things that makes a note a backlog item. The meeting notes
  and the READMEs arrive as top-level items.

Both reads route through `ownValue`. For `keyPresent`, `ownValue(fm, parentKey) !==
undefined` is the correct replacement rather than a second helper: a note carrying
`parent:` with no value parses to `null`, not `undefined`, so the empty "pinned to top
level" marker still reports present, which is the behaviour that marker depends on.

That this was missed is the finding, not just the fix. The audit that produced this
section counted four statements of the rule by grepping for `fm?.[`, and `in` does not
match that shape — so the search that found the defect was itself an instance of the thing
the register warns about: a check that agrees with what it was told to look for.

### Testing

The invariant test comes first and is watched failing, per the root `CLAUDE.md`:

- A note **without** an own `toString`, in a view whose horizon property is named
  `toString`, reads as **absent** — the item is unplaced, not shelved as unreadable.
- The same for the dated axis: `startProperty: toString` yields no bar rather than a
  refused one.
- A note that **genuinely owns** such a key still reads its value, so the fix is not a
  blanket refusal of exotic names.
- With `parentProperty: toString`, a note carrying neither a type nor a parent is
  **ignored**, not admitted as a pinned root — and a note that genuinely owns the key still
  links to its parent.

All five cases live in **one new file**, `test/domain/prototypeKeys.test.ts`, rather than
appended to `roadmap.test.ts` and `model.test.ts`. Measured: those sit at 419 and 422
effective lines against a 450 cap, so the axis block alone would have failed lint and Task 1
could not have finished — Codex's correction on PR #59. They belong together anyway: one
subject, one helper, one call rule.
- The existing `frontmatter.ts` suite must stay green across the import swap — it is the
  evidence that the moved helper is the same helper.

Revert the `readGated` line and the `resolveParent` reads, run, see red, restore.

## 2. `README.md` — two new sections

`## The board` and `## The roadmap`, as siblings after `Using the view`. The existing
tree prose is not rewritten: it is correct, and an additive diff is one a reader can
check against the code.

Both sections open with the same fact, because it is the one thing a user will otherwise
get wrong: **the projection is working position, not configuration.** It persists per
saved view per device in local storage, beside the collapse state, and never touches the
`.base`.

### `## The board`

- The toolbar toggle — the three positions are `Show as backlog tree`,
  `Show as kanban board`, `Show as roadmap`.
- One column per value in **Workflow states (in order)**, plus a column for items with no
  state at all; dropping a card there **removes** the property rather than blanking it.
  **Only the state property is required** — `workflowColumns` falls through
  `stateMenuValues` to the states the notes actually carry, so an unconfigured list draws
  the observed workflow rather than guidance, and a carried value the list omits still gets
  a column. Codex's correction on PR #59; the draft made both settings sound mandatory.
- **Focus decides what a card is**: `boardColumns` takes `model.focused ? model.roots :
  model.results`, so a focused board draws one card per focus-level item with its
  descendants beneath, not one card per backlog item. Codex's correction on PR #59 — the
  draft's opening sentence promised a card for everything.
- Three inputs, one move: drag, <kbd>Alt</kbd>+<kbd>←</kbd>/<kbd>→</kbd>, and the card
  menu's **Set state**, whose entries are the rendered columns.
- **WIP limits** — one per state **that is not a done state**: `progressGroup` omits the
  option for done values on purpose, because a finished column is a record rather than a
  queue. Policies are offered for every state, done included, so the two are not symmetric
  and the README must not imply they are. The limit reads the column's **full population,
  not the filtered count**, so narrowing the view cannot make an overcommitted stage look
  calm. It signals; it refuses nothing.
- **Policies** — a sentence per column, reachable from the column header and from the
  column menu.
- **Date stamps** — `started` and `finished` ride a state write, so neither fires without a
  state property. The two behave **differently across rework**, and the README must say so
  rather than flattening both into "write-once":
  - **`started`** is written only while the key is blank, so **the earliest start survives
    rework**. Re-entering a started state does not move it.
  - **`finished`** tracks the done boundary. Leaving a done state **clears** it — a reopened
    item must not claim a finish it no longer has — and completing again stamps the new
    date. Done-to-done is a re-labelling (`Done` becoming `Dropped`), not a new finish, so
    it writes nothing.

  Codex raised this on PR #59 against an earlier draft that said neither stamp is ever
  rewritten. That is true of `started` and false of `finished`, and the place it would have
  misled is exactly the reopen-and-recomplete workflow a board makes easy.
- Cards outside the base's filter render as context and carry no controls that would
  write to them.

### `## The roadmap`

- The axis is **declared in the view options, never guessed** from property names and
  never derived from dates.
- The axis picker — `Show horizons` and `Show timeline` — appears only when **both** axes
  are configured. With one, there is no choice to make.
- **Horizon buckets** from **Horizons (in order)** — the Now / Next / Later axis. Cards
  move between buckets by drag, by <kbd>Alt</kbd>+arrow or from the card menu, all three
  writing one value through the same gate, undoable as one batch. Each bucket creates in
  place.
- **The shelf** — everything unplaced, counted, and the drop target that *un-places*:
  dropping there removes the horizon key. It stays reachable while empty, because a
  target that exists only when occupied is one nothing can reach.
- **The dated axis** draws bars from a start and a target date property, and the two are
  **independently optional**: `hasDateAxis` is `startKey !== '' || targetKey !== ''`, so a
  target-only milestone roadmap and a start-only plan are both supported and both covered by
  tests. Describing the axis as needing two would make either sound unsupported — Codex's
  correction on PR #59. A parent with no dates of its own **spans its dated descendants**,
  drawn as the inference it is and written nowhere.
- **The dated axis is not read-only, and an earlier draft of this spec said it was.** With
  either date key configured, the row menu offers **Schedule** and **Unschedule**
  (`canSchedule` in `src/view/interactions/plan.ts`), which write through `applySafely` like
  every other batch. What `0.4.0` lacks is the **bar gestures** — dragging a bar to move it,
  its edge to resize, or an item off the shelf onto a date. The README must say *that*, not
  that the axis cannot be written: the draft carried a "Set dates → Schedule / Unschedule"
  row in the same table as the read-only claim, so it contradicted itself in eight lines.
- **Milestones** are a type of their own: on no rung, offered no child types, counted in no
  rollup, and reduced to their target date. **Stated as advisory, not enforced** — Codex's
  correction on PR #59. `isMarkerType` gates only the *offered* child types
  (`itemTypes.ts:102`), the autoType cascade, the rollup walk and which date ends apply;
  nothing refuses a milestone that is dragged under an item or given a `parent` by hand, and
  `linkAll` keeps the relationship. The draft said "no children, no parent" flatly, which
  contradicts the README's own existing sentence three sections above it — *"None of this is
  enforced. The ladder has always guided what the view offers and what it writes without
  refusing a move you make deliberately."*
- Planned dates are **different keys** from the board's transition stamps, so a plan can
  never overwrite a record.

## 3. `README.md` — three corrections

1. **`one of six` is wrong.** Line 30, and again at 328 and 331. `MARKER_TYPES` adds
   `Milestone`, so it is the ladder (`Epic → Feature → PBI → Task`), the extra types
   (`Issue`, `Bug`) beside it, and a marker on neither. This is
   [[Read the vocabulary instead of reciting it]] landing on the one file its sweep could
   not reach — that task reads `docs/`, and `README.md` is outside it. The correction
   follows that task's own step 3: **name the categories, not the count**, so the next

2. **The `View options` table is missing five groups**: *States that count as started*,

   the horizon / start / target property pickers.
3. **The `Using the view` table gains the projection toggle**, pointing at the two new
   sections.

## 4. `manifest.json` — the description

The current string describes a tree only. It is the community-directory listing — read
before installing, and unchangeable until the next release. It becomes:

> Display Bases results as a product backlog: a drag-and-drop tree of Epics, Features,
> PBIs and Tasks, a kanban board with WIP limits, and a roadmap, inspired by Azure DevOps
> Boards.

Marketplace constraints hold: sentence case, and **no special characters** — which is why
this reads `backlog:` and not `backlog —`. The em dash is the natural punctuation here and
is exactly what that rule exists to keep out of the manifest; the colon costs nothing.

`package.json`'s `description` gets the same widening. The two strings are **not** and have
never been identical — the manifest opens "Display Bases results as…", the package "Obsidian
Bases view that displays notes as…" — so each keeps its own opening and gains the board and
the roadmap.

## Recording the smoke test

The maintainer ran the tree, board and roadmap smoke tests in a `npm run test-build`
vault on 2026-08-02 and reported that everything went well. That closes the release's
largest risk: the roadmap had never been looked at at all.

It is recorded at the level the evidence supports, and no further. The three
`Smoke test the …` Feature notes get an **Outcome** naming the run, its date and its
result, matching the wording precedent in [[Smoke test the visual changes]]. The
"**Never checked**" warnings on [[Roadmap inferred bar appearance]] and
[[Roadmap milestone appearance]] are dropped, because they are now false.

**The Outcome paragraph is replaced, not appended to** — Codex's correction on PR #59. The
wording already there ("Every case below has been looked at, with the result written into
its own `Issue`'s Runs table") states the *convention* the register wants, in the perfect
tense, as though it had happened. Adding a sentence saying the per-case records do not yet
exist would leave one paragraph asserting both. A note that contradicts itself is worse
evidence than one that says nothing, which is the whole reason this section is careful.

**The sub-issues stay `Open`.** Each is a multi-point checklist whose acceptance criterion
is that every point is written down as pass or fail rather than assumed, and one of them —
[[Roadmap milestone appearance]] — has an outcome that is a *design decision*, choosing
between the three candidate fixes in [[Nearby milestone labels cover each other]]. Writing
twelve per-criterion verdicts from one sentence would be exactly the failure this register
exists to prevent: a note stating more than it observed. They remain open, with the run
recorded above them.

## Verification

`npm run check` — build, lint, coverage thresholds, fallow and the docs gate — green
before the commit, as always. Specifically:

- The docs gate must accept this spec (`docs/superpowers/` is exempt from work-item
  frontmatter; every wikilink in it still has to resolve).
- Coverage thresholds only ever rise. The `ownValue` change moves code between modules
  rather than adding branches, so the figures should hold; if the helper's `undefined`
  guard reads as an uncovered branch, it gets a test rather than a lowered threshold.
- `README.md` is prose and is gated by nothing. It is checked by reading it against the
  view options the code actually generates and the labels the toolbar actually sets —
  every claim in sections 2 and 3 above was taken from source, not from memory.

## What this pass does not claim

It does not make the roadmap's dated axis writable, does not split the view hub, and does
not lift a single documented limitation. It makes the plugin describe itself accurately
and stops one exotic property name from shelving a whole backlog. That is the whole of it.
