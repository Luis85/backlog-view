# A board scoped to one discipline

A board whose scope is a discipline, with a workflow of its own falling back to the
requirements board's field by field — [[A Deliverables board]]'s shape, so this is
[[Product Kanban]]'s board with a scope rather than a second board.

**Outcome** — A designer runs their own workflow — planned, research, designing, review,
validating, done — without leaving the backlog the rest of the team plans from.

*Barebones, and it starts from an argument this register has already had both ways.*
[[An Iterations board]] is **not** a precedent for it: that board reached for the same
field-by-field fallback and the reversal is recorded in the note — the user refused a second
workflow property outright, and it now reads the product state key and narrows that one
workflow into three buckets. What decided it there is the question to answer here first, in
its own words: two boards over the same population differ by which **states** matter, not by
which property holds them. A discipline board *is* over the same population, so the source
document's independently configurable workflow has to win that argument rather than assume
it. What the board inherits from its siblings — WIP limits, column policies, date stamps,
"show completed items" — is undecided, and each was a deliberate yes or no for the
Deliverables board.*
